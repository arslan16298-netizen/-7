# DECISIONS.md

## Вариант

Номер варианта: 2

Часть А: правило R4 — количество позиции в диапазоне [5, 100] вместо [1, 100]. Значение меньше 5 отклоняется
конструктором `OrderItem` и методом `setQuantity`. Границы заданы константами `MIN_QUANTITY = 5` и
`MAX_QUANTITY = 100` в одном классе `OrderItem`; `increase` проверяет итоговое количество (добавка 1 к позиции из 5 штук
допустима, итог 6).

Часть Б: `OrderService.addMinQuantityCheck(Order) → boolean` — `true`, если у всех позиций `quantity >= 5`
(цикл по `order.getItems()`). Для пустого заказа `true`, для `null` — `IllegalArgumentException("order is null")`.

## Решение 1

Формулировка: диапазон количества задан двумя константами в `OrderItem`, а единственная проверка диапазона находится в
private-методе `setQuantity`; конструктор и `increase` вызывают его, а не копируют условие.

Альтернатива: писать условие `quantity < 5 || quantity > 100` отдельно в конструкторе и в `increase`.

Обоснование: вариант 2 изменил одно правило, и оно меняется в одной строке (константа). `Order`, `OrderService` и
`SelfCheck` читают `OrderItem.MIN_QUANTITY`, поэтому порог не размножен по классам.

## Решение 2

Формулировка: логика объединения повторов (R7), запрет изменений после `confirm` (R8) и итог (R9) находятся в `Order`;
`OrderService` без полей только создаёт заказ и анализирует его. `removeProduct` для отсутствующего id выбрасывает
`IllegalArgumentException`, а не молча ничего не делает.

Альтернатива: вынести объединение в `OrderService` или игнорировать удаление несуществующей позиции.

Обоснование: `Order` — корень агрегата и сам знает свой состав и статус, поэтому проверки не обойти. Контролируемая
ошибка при удалении не скрывает опечатку в id.

## Ответы на контрольные вопросы

### Вопрос 1

Наиболее вероятная ошибка входных данных — количество вне допустимого диапазона, потому что оно приходит из внешней
строки CSV или от пользователя. Её перехватывает проверка `quantity < MIN_QUANTITY || quantity > MAX_QUANTITY` в private-методе
`setQuantity` класса `OrderItem`; её вызывают конструктор и `increase`. По варианту 2 значения 0–4 и 101 и больше дают
`IllegalArgumentException("quantity must be in [5, 100], got N")`, а позиция в заказ не попадает. Рядом стоят проверки
`price > 0` и `isBlank` в конструкторе `Product`. Строковые ошибки (нечисловая цена, пробелы вокруг значения) отдельно
ловит разбор строки в `SelfCheck`, поэтому программа не падает, а выводит понятное сообщение.

### Вопрос 2

Ключевое бизнес-правило — объединение повторов R7 вместе с запретом изменения подтверждённого заказа R8; оба находятся
в методе `Order.addProduct`. Метод сначала вызывает `requireDraft()`, затем ищет позицию с тем же id и либо вызывает
`increase`, либо создаёт новую `OrderItem`. Я разместил правило в `Order`, потому что заказ — корень агрегата: он владеет
списком позиций, знает статус и отдаёт наружу только `List.copyOf`. Внешний код не может добавить позицию в обход
проверок. Если бы правило жило в `OrderService`, любой код мог бы вызвать `getItems()` и нарушить его.

### Вопрос 3

Ромб «Товар с таким id уже есть в заказе?» на Activity-диаграмме соответствует вызову `findItem(product.getId())` в
`Order.addProduct`. Ветка «да» ведёт в блок «Увеличить количество существующей позиции», то есть в
`existing.increase(quantity)`; ветка «нет» — в блок «Создать новую позицию», то есть `items.add(new OrderItem(...))`. Затем
оба пути идут в ромб «Итоговое количество в диапазоне 5–100?», который в коде реализует `setQuantity`; ветка «нет» ведёт к
исключению, и заказ не меняется. Для строки `M01;...;3` при существующей позиции из 5 штук путь: товар корректен, заказ DRAFT, товар есть, итог 8, допустимо.

### Вопрос 4

Минимального числа изменений требует смена границ количества, например с [5, 100] на [10, 50]. Меняются только две
константы `MIN_QUANTITY` и `MAX_QUANTITY` в классе `OrderItem`, то есть один класс и две строки. Текст сообщения
об ошибке собирается из этих констант, поэтому правится сам собой; логика `Order`, `OrderService` и диаграммы не
затрагиваются. Потребуется только обновить ожидания в `SelfCheck` и строки `sample.csv` с границами. Локальность
достигнута тем, что единственная проверка диапазона находится в `setQuantity`, а остальные классы читают константы.

## Фрагмент кода для анализа

```java
public List<OrderItem> items = new ArrayList<>();
public List<OrderItem> getItems() { return items; }
```

Ошибка в нарушении инкапсуляции: наружу отдаётся ссылка на внутренний изменяемый список, а само поле открыто. Внешний код
может выполнить `order.getItems().add(new OrderItem(...))` и обойти `addProduct`, то есть R7 (повтор станет второй
строкой), R8 (позиция добавится в подтверждённый заказ) и проверку количества. Исправление: поле `private final`, а
геттер возвращает `List.copyOf(items)`; изменения идут только через `addProduct` и `removeProduct`. Это правило R11:
состав заказа меняет только сам `Order`, поэтому инварианты нельзя нарушить снаружи, а попытка изменить копию даёт
`UnsupportedOperationException`.
